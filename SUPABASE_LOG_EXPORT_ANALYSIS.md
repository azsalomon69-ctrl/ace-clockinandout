# Supabase log export analysis

**Source:** `C:\Users\azsal\Downloads\supabase_logs (1).csv`  
**Scope:** 1,000 exported log rows, from 2026-09-29 12:58:59 to 17:31:58 (about 4 hours 33 minutes). This is a static export; it does not provide live billing totals, untruncated payload sizes, or a declared export limit.

## Bottom line

The export proves that application/API request logging—not Postgres checkpoint logging—is the dominant producer in this window. It also proves severe request bursts: one minute contains 294 log rows and one second contains 44 rows.

The two principal paths are `/rest/v1/profiles` and `/auth/v1/user`. They account for 722 of the 946 Edge/API rows (76.3%). The deployed cache/coalescing changes directly target this pattern. However, this 1,000-row CSV cannot by itself prove what produced the approximately 1 GB platform ingestion charge: its displayed event-message text is only about 138 KB in total and does not equal Supabase's ingested-byte accounting.

The busiest seconds in the entire export contain 44, 42, 36, 35, and 29 requests. The request shape is an application initialization/admin-dashboard fan-out with redundant authentication and profile activity, not a smooth database maintenance stream.

## What this means for the implemented reductions

The backend's short-lived, coalescing authentication/profile cache is aimed at the 304 GoTrue validations and the overlapping profile reads generated by parallel protected API calls. Eliminating GoTrue `admin/users` sweeps removes another repeated producer. The browser's longer heartbeat reduces recurring status/profile writes.

These changes should materially reduce the observed request count, especially page-load bursts. They do not guarantee a proportional reduction in billed bytes: Supabase bills ingestion across services and includes platform-side log representation not present in the CSV's `event_message` column.

## What remains unproven about the 1 GB figure

1. The export has a fixed 1,000 rows and does not establish whether it covers the exact high-ingestion hour or is truncated.
2. The `event_message` field is not a byte-usage meter. Across all rows its visible text is only roughly 138 KB.
3. The export cannot show other service logs or time ranges that may dominate the billing window.

Before attributing the full 1 GB to this bug, capture the Supabase Usage graph and Logs Explorer for the same billing period, grouped by service and bytes where available. Capture one representative hour before deployment and the comparable hour after deployment. If the expected Edge/Auth reduction is absent, use the top remaining service/path in that comparison as the next target.

## Do not change first

Do not disable Postgres checkpoint logging based on this export. It represents 54 rows (5.4%) and Supabase describes checkpoint logging as normally low volume. Leave it available for database health diagnosis unless a byte-based dashboard view specifically proves otherwise. See [Supabase log-ingestion guidance](https://supabase.com/docs/guides/platform/manage-your-usage/logs-ingest).
