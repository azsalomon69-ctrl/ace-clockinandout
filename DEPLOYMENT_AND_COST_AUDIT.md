# Deployment, service usage, load, and cost audit

Date: 2026-09-30. This is a read-only repository audit plus current vendor documentation research. It does not inspect the Render or Supabase dashboards, deploy history, billing invoices, DNS, or live credentials. Statements labelled **confirmed from repository configuration** describe the intended deployment; dashboard-only facts are explicitly marked unknown.

## Bottom line

The stack is technically appropriate for 30-100 users. The immediate reliability problem is **not Supabase or Render as vendors**. It is that the configured backend is a **Render Free web service**, which can sleep after 15 minutes and take about a minute to wake, and can restart at any time. That is unsuitable for a clock-in/clock-out system where a failed or delayed clock action matters.

Paying for the smallest always-on Render web service (currently listed at $7/month) is the one change worth making first. Do not migrate the database, Auth, or frontend to solve a problem that is principally a free-tier availability problem.

### Database connection topology

There is **no direct `pg`, `postgres`, Prisma, TypeORM, or PostgreSQL connection string** in source or dependencies. Every backend database call goes through one `@supabase/supabase-js` client:

```text
Browser → Render Static Site → Render API (Express)
                                   ├─ Supabase GoTrue HTTPS APIs (token validation/Admin API)
                                   └─ Supabase PostgREST HTTPS APIs (table queries and RPCs)
```

| Code path | Connection method | What it does |
|---|---|---|
| `backend/server/index.js:9,17-19` | `createClient(SUPABASE_URL, SUPABASE_SECRET_KEY)` | One server client with SDK auth-session persistence/refresh disabled. This is an HTTPS Supabase client, not a Postgres socket/pool. |
| `backend/server/index.js:34,300-305,360,369,376,393-995` | `db.from(...).select/insert/update/delete/upsert(...)` | Supabase JS PostgREST calls for all application table access. |
| `backend/server/index.js:630,641,652,661,671,683,839,851,863,878,890,918,929,936` | `db.rpc(...)` | Calls PostgreSQL functions through the Supabase RPC/PostgREST layer. |
| `backend/server/index.js:287-291` | `db.auth.admin.listUsers()` | GoTrue Admin API call for Google-avatar enrichment only. |
| `backend/server/index.js:294-315` | `db.auth.getUser(token)` | GoTrue API validates every protected request's bearer token; then the API loads `profiles` and applies its own role/status checks. |
| `frontend/js/supabase-auth.js:9-17,23,34-45`; `frontend/js/script.js:2339-2341,2370-2383` | Browser Supabase Auth SDK | Constructs the client from `/v1/auth/config`, performs Google OAuth, reads/persists/refreshes session, and signs out. It sends the bearer token to Express. |

The backend does **not** keep long-lived PostgreSQL connections and has **no connection pool**, because it never uses the Postgres wire protocol. It keeps an SDK client object, which issues HTTP requests to Supabase. That avoids direct connection exhaustion today, but adds a network hop and makes every protected API request depend on GoTrue token validation.

### Auth truthfully described

This is **Supabase Auth (GoTrue) plus Google OAuth**, not a custom identity system. The custom layer is only the application authorization/profile layer:

1. The browser starts Google OAuth through GoTrue.
2. GoTrue manages the browser session and issues the access token.
3. The browser passes that token to the backend.
4. The backend calls GoTrue `auth.getUser(token)` to validate it, then loads `profiles`.
5. Backend middleware decides active/admin/special-admin and ownership access (`backend/server/index.js:294-320`).

So **both** participate: GoTrue authenticates the token; backend code authorizes the resulting user. The backend does not locally verify JWT signatures or rely on custom JWT claims. Its operational dependency is a network call to GoTrue on every protected request.

## 5. Render-specific constraints and failure modes

### Current reality

* **No Postgres pool:** as described above, all data calls are outbound HTTPS via Supabase JS.
* **Free-tier cold starts are real:** Render spins down a Free web service after 15 minutes without inbound traffic; the next HTTP/WebSocket request spins it up and takes about one minute. Render explicitly says Free is not for production. [Render Free limitations](https://render.com/docs/free)
* **Free can restart at any time** and cannot scale beyond one instance. A restart terminates SSE streams and clears process memory. [Render Free limitations](https://render.com/docs/free)
* **In-flight clock operations:** an in-flight HTTP request can be interrupted by restart/deploy/network failure before its response reaches the browser. The database RPC may have committed, may have rolled back, or (depending on timing) the client may not know. Existing transactional/idempotent SQL reduces duplicate-write risk, but the client needs a reconciliation read after an ambiguous failure. This cannot be proven end-to-end without staging credentials and restart testing.
* **In-memory state that is lost or becomes inconsistent across instances:**
  * `chatSubscribers` SSE connections (`backend/server/index.js:23-37,544-563`): lost on restart; events cannot cross instances if you later scale.
  * `express-rate-limit` default memory stores (`79-100`): reset on restart and apply per-instance after scaling. They are best-effort throttles, not durable/global enforcement.
  * Node process state only; there is no server session store. Browser/GoTrue sessions are safe from backend restart.
* **Auto-scale consequence:** Free cannot scale. On paid multi-instance Render, ordinary stateless API routes should work because state is remote, but chat SSE delivery will be per-instance only; a sender and recipient on different instances will not receive live event notifications. Refresh/reconnect still sees data in Postgres, but “live” chat degrades.
* **Logs:** morgan logs every request in production (`75`). The 45-second heartbeat makes log volume grow rapidly. This is a cost/noise/diagnostics issue, not a correctness blocker.

### What to verify live (not performed)

No staging credentials are configured locally. Before relying on any inference, do these dashboard/staging checks:

1. Verify the live Render service plan, region, branch, auto-deploy setting, number of instances, deploy history, and actual frontend Static Site URL.
2. Confirm Supabase plan, project region, database size, MAU, egress, Auth usage, and backup status.
3. On staging, submit clock-in/out while triggering a safe service redeploy/restart; then reconcile final time-entry/audit state and retry behavior.
4. Keep two chat clients connected through a restart; ensure client reconnect works and messages remain correct.
5. Inspect request logs for heartbeat and full-history time-entry load volume before optimizing.

If you move the database first while retaining Supabase Auth, the hidden complication is that Supabase Auth's `auth.users` schema presently owns the profile FK and trigger. A plain Postgres host can receive the public application data and functions, but it cannot simply host a live Supabase Auth schema unless you also operate a compatible Auth deployment. That makes “DB only” a nontrivial hybrid migration; the previous Supabase-dependency audit gives the detailed sequence.

## 7. Honest recommendation

**Keep the current stack.** Supabase Postgres/Auth plus one Render API is not remotely a scale problem for 30-100 users. The app's database access is already behind the backend, PostgreSQL is the correct engine for clock correctness, and the browser does not need a rewrite.

**Fix first: upgrade the Render API off the Free plan.** The confirmed free configuration creates a predictable one-minute cold-start path after 15 idle minutes and permits arbitrary restarts. That is the only presently demonstrated infrastructure mismatch with reliable clock actions. The smallest published paid Render web plan is $7/month. Do this before considering a migration.

**Second, only after observing logs:** reduce the 45-second presence write frequency and stop loading complete time-entry history on every app initialization. These are concrete code-driven sources of avoidable load. They do not justify Redis, a queue, or a new managed service.

**Do not move Supabase or Auth now.** A database-host migration has materially more risk than value at this scale, while Auth replacement is the hardest change in the system. Revisit the choice only for a specific driver: compliance/data residency, unacceptable provider outage history, required private networking, sustained usage past quotas, or a business requirement to own identity operations.
